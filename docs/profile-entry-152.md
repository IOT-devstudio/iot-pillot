# 报名资料入口按完整状态切换（#152）

基线：main `db72953`。本次只改前端。后端报名鉴权与资料契约（`PUT /me` 字段、`SubmitToRound` 快照）一律不动。

## 目标

- 报名弹窗的「资料」行按真实完整状态显示「查看资料」或「完善资料」。
- 资料不完整时，弹窗内的报名动作不提交申请，直接跳转个人设置页补全。
- 补全保存后返回首页，入口自动切到「查看资料」。
- 判定与登录后的补全提醒共用同一套规则，不按页面另定必填项。

## 判定：四态入口

唯一判定来源是 `apps/web/src/modules/user-settings/profileCompletion.ts` 的 `missingRequiredProfile`（班级 + 学号）。本票在 `modules/home/` 新增一个纯函数把它翻译成入口状态，首页三处入口共用同一个结果：

| 状态 | 条件 | 入口文案 | 报名动作 |
| --- | --- | --- | --- |
| `ready` | 读到 `detail` 且班级、学号都有效 | 查看资料 ↗ | 放行 |
| `needs-completion` | 读到 `detail` 且明确缺字段 | 完善资料 ↗ | 拦截 → `/user/settings?from=apply` |
| `unknown` | 资料加载中、读取失败、或没有 profile | 个人资料 ↗ | 放行 |
| `hidden` | `is_founding === true` | 不渲染入口 | 放行 |

三条硬规则：

- **fail-open**：只有「明确读到资料且确实缺字段」才拦截。加载中、`/me` 失败、`detail` 缺失一律放行——接口抖动不能变成「报名按钮点不动」。
- **创始管理员豁免**：该账号被 `denyFounding` 挡在设置页外，若参与门槛会形成一次无效往返。
- **文案中性**：`unknown` 用「个人资料」而不是「查看」或「完善」，不假装知道状态。

## 交互

### 报名弹窗

- 「资料」行改为按状态渲染：`ready` / `needs-completion` / `unknown` 三种文案，`hidden` 不渲染（沿用现在「创始账号」的占位）。
- 两个报名动作（「报名 · 无需填表」与「面试 · 填写该方向表单」）进入时先判状态。`needs-completion` 时：关闭弹窗、走壳层擦除转场跳转 `/user/settings?from=apply`，**不发任何写请求**。
- 拦截必须有可见反馈：跳转后由设置页顶部的提示条说明原因，避免用户以为点击失效。

### 个人设置页

- 新增 `useRoute`，识别 `from=apply`。
- `from=apply` 且仍缺字段时：自动进入编辑态，顶部提示「报名前请先补全：班级、学号」（只列缺失项），并在补全后随 `needsCompletion` 消失。
- `from=apply` 但资料已完整（旧链接、或另一标签页已补全）：不提示，停在正常只读态。
- 保存成功后 `save()` 已经把 `editing` 置回 `false`，不需要额外处理。

### 首页另外两处入口

统计区资料卡（`UserHomeView.vue:588-594`）与收尾区（`:756-762`）现在无条件写「完善我的资料」。只改弹窗会造成同页三种说法，三处一并按同一状态切换；`hidden` 时保持现在的隐藏行为。

全局的 `ProfileCompletionNotice` 不动：它是登录后的常驻提醒，不是报名入口，语义不同。

## 接口

无新增接口。判定数据来自 `GET /api/v1/me`，补全走 `PUT /api/v1/me`，报名仍是 `POST /api/v1/recruitment/applications`，本票只在调用前加一道前端判定。

## 边界

- **不是鉴权**：后端不校验资料完整性，直接调 API 仍可提交空资料。这是体验层门槛，不能对外宣称「资料不全无法报名」。
- **表单填写页不拦**：`/f/:shareToken` 属于外部分享场景，从那里提交同样走 `SubmitToRound`、落同一条申请与同一份快照。本次不拦，单独开 follow-up 记录。
- **已有申请不受影响**：申请里的资料是提交时快照，不回溯。
- **新用户会多一跳**：注册（`RegisterReq`）只收姓名/密码/邮箱/验证码，不含班级学号，因此每个新用户首次报名都会被引导去补全。这是产品取舍，已知并接受。
- **面试路径同样拦截**：面试表单提交与直接报名产生同一种申请，只拦报名会留下明显旁路。

## 保存后返回的状态一致性

首页的判定直接读共享的 `currentProfile`（`UserHomeView` 里现有的 `user`），不另存一份快照。两条路径分别看：

- 点「保存」后返回：`save()` 内部 `hydrate` 已发布新资料并把 `editing` 置回 `false`，返回首页没有竞态。
- 改了没点保存直接离开：`onBeforeRouteLeave` 触发 `autoSave()`（未 await），存在一个短暂窗口。`profileIdentity.beginProfileLoad` 的 revision 守卫会丢弃在途的旧 `/me` 结果，PUT 成功后发布新值，界面自愈。

因此**不改** `onBeforeRouteLeave` 的时序（会牵动 #159/#183 的既有行为）。若验收时仍观察到偶发旧态，再单独把离开保存改成 await。
