# Issue #107 数据库迁移实施计划

目标：保留 #85 前端分支，从 main 独立交付数据库迁移工具和部署前置闸门。

依据：https://github.com/IOT-devstudio/iot-pillot/issues/107 与 2026-10-14 交接文件。
执行方式：本会话按用户已确认方案顺序实施，无生产数据库操作。

## 约束与设计

- 0001–0009 SQL 保持原样；采用固定版本 golang-migrate 库，构建独立 `iot-migrate` 命令。
- `up` 对空库按序执行，对未纳管的已有库拒绝自动重放。
- `check/adopt --applied` 接受明确的手工迁移清单，在事务内创建隔离参考 schema，执行清单中的原 SQL，比较列类型、默认值、空值约束、索引和约束。参考事务始终回滚。
- 验证通过才记录已执行迁移及 SQL 校验和；migrate source 对这些版本返回空操作，其余版本仍执行原 SQL。支持非连续清单，禁止直接 force 最大版本。
- 不自动 down；失败保留旧容器，迁移成功后的应用回滚要求旧代码兼容新结构。生产首次接管先备份并在已有库副本验证。

## 实施阶段

- [ ] 核心工具：先添加真实 PostgreSQL 集成测试，覆盖空库、非连续接管、结构不符、重复执行、dirty 状态和锁；实现工具并验证，提交第一阶段。
- [ ] 部署：镜像携带工具和 SQL，SSH 在 stop/rm 之前运行迁移容器；打桩断言失败不停止旧容器、不推进水位。CI 和部署 runner 使用临时测试数据库验证工具，提交第二阶段。
- [ ] 文档与检查：同步 README/架构/决策日志/迁移操作说明，运行 Go 检查和部署打桩，审阅 diff 后提交第三阶段。

## 审阅重点

低编号遗漏不得被高编号掩盖；错误清单和已有列类型漂移必须拒绝；已上线索引不能重建；失败重试不能自动清除 dirty；连接凭据不出现在命令行和错误日志。
