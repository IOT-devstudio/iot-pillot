# ADR 0007：问答回复的邮件通知走有界队列、失败不影响回复

## 状态

已确认（2026-10-30）。来自地图 #207「[探索地图] 招新问答与学习路线」的决策票 #212「[通知] 问答回复邮件通知接入点定稿」。

**未落地**：本文只记录通知链路的决策，实现见后续实施票。

## 上下文

地图 Notes 里已锁定一条边界：「复用 `MailModule` 发邮件，**仅**『我的提问被回复』触发」。本票要把这句话落到可实现的形状上：模板怎么配、什么时候发、发不出去怎么办。

调研确认的事实：

- `apps/api/internal/utils/mail_util.go:41-70` 的 `SendEmail` 给整次发送加了 10 秒等待上限，注释明确写出局限：**超时只是让调用方不再等待，被卡的 goroutine 与 TCP 连接会一直占用到对端超时**。也就是说「同步发」的代价上限不是 10 秒，而是 10 秒 + 一条泄漏的连接。
- `deletion`（`apps/api/internal/service/mail_usec.go:334-378`）与 `freeze`（同文件 `:380-428`）已确立「模板没配就用内置默认文案」的范式，`apps/api/internal/repository/mail_repo.go:79-90` 的 `GetByType` 也明确「没有模板是合法状态而非错误」。
- `RenderTemplate`（`apps/api/internal/utils/mail_template.go:29-58`）遇到模板里出现但调用方没提供的变量会**直接报错**，不是渲染成空字符串。
- `apps/api/internal/handler/router.go:283-296` 已有「后台任务随服务 Start/Stop、先收尾再等在途请求」的装配范式（`FreezeScheduler`）。
- 仓内**没有任何站点域名配置**：`apps/api/internal/config/config.go` 只有 SERVICE / CORS / DB / SMTP / REDIS / JWT / CACHE / AUTH / DOCS，`.github/workflows/deploy.yml` 里也没有站点 URL。
- 回复正文上限 20000 字符（ADR 0005）；Markdown 剥离能力在**前端** `markdownExcerpt`，后端没有对应实现。

## 决策

### 1. 一个模板类型 `qa_reply`，两个内容域共用

通知正文对 `scope` 不敏感（都是「你的帖子有新回复」），一套模板够用。`scope = studio` 的帖子被回复时**同样发信**，通知逻辑挂在「创建回复」这个动作上，不读 scope。

管理端模板类型的下拉是**固定枚举**（`apps/web/src/modules/mail/components/TemplateEditorDialog.vue:162-165` 现在只有 invitation / offer / rejection / custom），需要加一项 `qa_reply`。`type` 的唯一索引已在迁移 0005 降级成普通索引，同类型可以多条。

### 2. 没配模板就用内置默认文案，照发

沿用 `deletion` / `freeze` 的范式：`GetByType` 返回 nil 时用内置文案，不把「管理员忘了建模板」变成「通知功能不存在」。

内置文案**只引用 `render` 预填的变量**（`{{name}}` 等），绝不引用需要调用方额外传的变量 —— 否则内置兜底本身会变成一个新的失败点。

### 3. 有界队列 + 单 worker，随服务启停

回复接口**不等 SMTP**。通知投递进一个有缓冲上限的 channel（容量 256），由一个常驻 goroutine 串行消费；`Start` 在 `ListenAndServe` 之前，`Stop` 在 `shutdown` 之前，与 `FreezeScheduler` 同一位置。

- **队列满 → 非阻塞丢弃 + 记日志**。回复绝不能因为通知队列满而变慢或失败。无界队列只是把「无限起 goroutine」换成「无限吃内存」，在 SMTP 卡死时同样拖垮进程。
- **单 worker**：SMTP 会话本来也不适合并发爆破；单 worker 让「同时在途几封信」这个数可数。
- **Stop 时不再接新任务，已入队的尽力发完，最多等 5 秒**：保证发版不会因为 SMTP 卡住而拖长退出时间。

### 4. 通知失败不回滚回复

招新流程的既有不变式是「邮件投递失败不落业务状态」（`apps/api/internal/service/recruitment_invitation_usec.go:529-535`：邮件先行、失败即返回、状态与时间线都不动）。**这里不沿用**，因为两者邮件承担的角色不同：

- 招新那边，发邀请**就是**那个动作本身 —— 邀请没发出去，「已邀请」这个状态就不成立，必须拦住。
- 这里，**回复**才是用户的动作，邮件只是附带通知。把通知失败变成「回复失败」，用户重写的内容会丢，重试还会产生重复回复。

### 5. 收件人：帖子作者，跳过自己，空邮箱跳过

- 只发给**帖子作者**（不发给其它回复者 —— 本期没有「订阅本帖」的概念）。
- **自己回复自己的帖子 → 跳过**，不发。
- 作者邮箱为空 → `sendWithTemplate` 会返回「该用户没有邮箱，无法发送」，按失败记日志跳过，**不为没有邮箱的账号编造收件地址**。

### 6. 每条回复都发，不合并、不限频

帖子的回复量是个人对话量级，不是事件流。合并要引入延迟投递窗口与「已合并」状态，还要处理进程重启时窗口丢失 —— 与「本期最简」直接相悖。

已知代价：某个热帖被连续回复时，作者会收到连续多封。这是可接受的，且比「悄悄少发一封、用户永远不知道为什么」更好解释。

### 7. 不给链接，只给标题 + 摘录 + 发信人

邮件内容 = 帖子标题 + 回复正文摘录 + 发信人姓名。**不拼站内链接**：拼链接要新增一个部署必配的站点 URL 配置项，配错比没有更糟（点进去 404）；用请求 Host 头拼则在异步发出时可能拿到内网地址，且 Host 可被伪造。

### 8. 摘录：后端按字符截断 200，原样保留 Markdown 源码

用 `[]rune` 截断保证不切坏中文与 emoji。不引入后端 Markdown 剥离：同一套规则在 Go 与 TS 各写一份，漂移时邮件与页面显示不一致。用户看到少量 `**` 标记是诚实的 —— 那就是他回复的原文。

### 9. `mails` 不加来源列

系统发起的邮件 `operatorID` 传 0，与「管理员手动发」天然分开（`freeze` 通知已经这么做，`mail_usec.go:426-427` 注释写明「发信记录里 from_user_id = 0 正好与管理员手动发送区分开」）。管理端没有「按来源看通知」的需求，为零消费者加列是过度设计。

### 10. 只有「新建回复」触发，编辑不再通知

编辑是修正笔误，不是新的交流事件。再发一次会让「有人回你」这个信号贬值。

### 11. 失败只记日志，前缀 `[forum]`

日志带 post id / reply id / 收件人 id。不往 `mails` 表写失败记录（那张表的语义是「已发出的信」，塞失败记录会污染记录页与统计），不加 Redis 计数器（本期没有指标采集端）。

## 拒绝的方案

| 方案 | 原因 |
| --- | --- |
| 两个模板类型（`qa_reply` / `forum_reply`） | 通知正文对 scope 不敏感；两个类型要配两条模板，漏配一边就少一类通知 |
| 复用 `custom` 类型 | `custom` 是手工发信的通用类型，通知要靠「按名字找模板」这种隐式约定，改个名字就断 |
| 没配模板就不发 | 上线初期没人配模板 = 通知功能实际不存在，用户无从得知 |
| 没配模板就报错、回复失败 | 把运营疏忽直接变成用户无法发回复 |
| 裸 `go func()` 火忘 | 无并发上限；进程重启/发版时在途的那封直接丢，且丢了没人知道 |
| 同步发（回复接口最多多等 10 秒） | SMTP 半死不活时用户点「回复」要转 10 秒；且被卡的 goroutine 还占着连接 |
| 无界队列 | 只是把「无限起 goroutine」换成「无限吃内存」，SMTP 卡死时同样拖垮进程 |
| 队列满就阻塞等 | 回复请求被通知队列连带卡住，违背「通知失败不影响回复」 |
| 队列满改成同步发 | 同一个接口有时快有时慢 10 秒，两套失败路径叠在一起 |
| 4 个以上 worker | 本期量级用不到；SMTP 会话并发、失败重试交织更难推理 |
| Stop 时直接丢弃队列 | 发版瞬间那批通知静默消失，日志里看不出丢了几条 |
| 通知失败回滚回复 | 用户写好的回复因 SMTP 故障丢失，重试产生重复回复 |
| 失败状态落到回复行上（加一列） | 本期没有重发通知的入口，这一列除了让人看见失败之外没有消费者 |
| 通知所有回复者 | 本期没有「订阅本帖」概念，会把帖子变成群聊 |
| 不跳过自己回复自己 | 自己收到自己的通知是纯噪音 |
| 邮箱为空时回落成待办/站内信 | 本期没有站内信机制，等于新建一套 |
| 合并同一帖子的多条回复 | 要延迟投递窗口 + 「已合并」状态 + 进程重启时的窗口恢复 |
| 每人每天限 N 封、超出丢弃 | 被丢掉的那条用户永远不知道，「为什么这条没通知我」无法解释 |
| 邮件里拼站内链接 | 要新增部署必配的站点 URL；用 Host 头拼在异步发出时可能拿到内网地址且可伪造 |
| 后端也写一个 Markdown 剥离函数 | 同一套规则 Go 与 TS 各写一份，漂移时邮件与页面不一致 |
| 邮件正文不放摘录 | 收件人必须回站内才知道说了什么，邮件的信息量降到接近标题党 |
| 内置模板引用 `{{post_title}}` 等新变量 | `RenderTemplate` 缺变量直接报错，内置兜底会变成新的失败点 |
| `mails` 加 `source` 列 | 要改表 + repo 接口 + 管理端筛选，而管理端没有按来源看通知的需求 |
| 失败记录写进 `mails` 表 | 那张表语义是「已发出的信」，塞失败记录会污染记录页与统计 |
| 编辑回复也发通知 | 通知频率翻倍，且「编辑」与「补充」在数据上无法区分 |

## 后果

**新增 1 个 service 组件**：通知队列（有界 channel + 单 worker + `Start`/`Stop`），装配位置对齐 `apps/api/internal/service/freeze_scheduler.go` 与 `apps/api/cmd/wire.go:81-83`。

**新增 1 条内置模板**：`qa_reply` 的内置兜底文案，形态对齐 `builtInDeletionMail` / `builtInFreezeMail`。

**改动 1 处前端**：`TemplateEditorDialog.vue` 的模板类型下拉加一项 `qa_reply`。

**不改 schema**：`mail_models` 与 `mails` 都不需要迁移。

**可逆性边界**：换成同步发只需把入队调用改成直接调用，队列组件可整体删除；换成合并语义则要新增延迟窗口与状态，那时队列已经是正确的位置。但「通知不回滚回复」这条是**单向的** —— 一旦用户习惯了「回复成功即成功」，再改成回滚会让既有回复的语义发生变化。
