# ADR 0004：附件上传链路与正文图片引用

## 状态

已确认（2026-10-30）。来自地图 #207「招新问答与学习路线」的决策票 #210「[图片] 上传链路与前端交互定稿」。

**未落地**：本文只记录上传 / 读取端点、正文引用语法与前端交互的决策，建表见 ADR 0003，部署见 #213，Markdown 渲染见 #214。

## 上下文

ADR 0003 已定 `content_attachments` 表：`post_id` / `reply_id` / `roadmap_id` 三列全可空，三列全空即**孤儿态**，24 小时未绑定即清理。ADR 0002 已定图片存 MinIO 私有 bucket、经 Go 代理转发、上传走服务端中转。

剩下没定的是**链路**：端点长什么样、正文怎么引用图片、绑定集合以谁为准、失败与配额怎么处理。

调研确认的既有事实：

- `apps/web/src/api/auth.ts:64-67` 的 `requestBackend` **写死 15000ms 超时**，没有超时参数。
- `apps/api/internal/utils/limiter.go:143-172` 的 `Limiter` 只有 `AllowOnce` / `AllowWithin` / `RecordFailure`，窗口是**自首次计数起算的固定窗口**（`RedisCounter.Incr` 仅在 count==1 时设 TTL），不是自然日。
- 前端全仓**无** `createObjectURL` / `Blob` / `el-upload` / `el-image` / `type="file"`，图片上传交互从零开始。
- 后端**无**任何 multipart 处理。

## 决策

### 1. 两个端点，都只挂 `authRequired`

| 端点 | 用途 | 鉴权 |
| --- | --- | --- |
| `POST /api/v1/attachments` | 上传一张图 | 只要求登录 |
| `GET /api/v1/attachments/:id` | 读取一张图 | 只要求登录，**归属在 handler 里解析** |

上传端点**不分 scope**：附件表没有 scope 列，上传时服务端根本不知道这张图将来会落到招新问答、内部论坛还是学习路线（用户是「边写边传」，正文还没提交）。让上传带 scope 就必须给附件表加列，与 ADR 0003 已定稿的迁移冲突。

读取端点同样只有一条路由，归属判定在 handler 内：

| 附件状态 | 谁能读 |
| --- | --- |
| 未绑定（孤儿态） | **仅上传者本人** |
| 绑定到 `scope = studio` 的帖子 / 其回复 | 需管理员 |
| 绑定到 `scope = recruitment` 的帖子 / 其回复 | 登录即可 |
| 绑定到学习路线 | 登录即可 |
| 所属帖子已软删 | **404**（按不存在处理） |

无权访问一律返 **404 而非 403**：不泄漏「这个 id 存在但你没权限」，避免被用来枚举内部论坛的内容规模。

### 2. 正文用标准 Markdown 引用真实端点

正文里写 `![图1](/api/v1/attachments/123)`，**不用** `attachment:123` 之类的自定义 scheme。

渲染层（#214）因此完全不需要知道附件系统的存在，Markdown 库按普通图片处理；XSS 白名单也不用额外放行一个自定义协议。代价是正文里存了带前缀的相对路径，将来换 API 前缀要迁移数据——接受，因为前缀在 `router.go` 里是常量，迁移概率低。

外链图片（`![](https://...)`）**允许**，渲染时照常显示：Markdown 的本意就是能引外链，且外链图不泄漏任何私有内容。

### 3. 绑定集合的唯一真源是**正文**，服务端解析

发帖 / 回复 / 编辑的请求体**不带** `attachment_ids`。服务端从 `body` 里正则提取 `/api/v1/attachments/(\d+)`，去重后的 id 集合即绑定集合，在同一事务里 UPDATE 绑定。

这条推翻了本票第 1 轮「请求体带 `attachment_ids`」的初步结论：如果同时存在「请求体数组」和「正文语法」两个来源，就有两个真源，前端改解析规则会悄悄改变绑定结果，服务端也无法验证。**声明式重算**让正文成为唯一真源：

- 新建：正文里出现的 id 集合 = 绑定集合。
- 编辑：与新建走**同一套** service 逻辑，编辑后消失的 id 解绑回孤儿态，24h 后由清理任务回收。新建与编辑只有「作者本人或管理员」的归属校验不同。
- 重算遇到非法 id（不存在 / 别人上传的 / 已绑在别的帖子）→ **整次保存失败**，返回精确错误（如「图片 123 无权使用」），让用户自己改正文。不静默忽略（会留下 404 语法），不静默改写正文（服务端擅改用户内容）。

必须**只匹配本站前缀**，外链图片不参与绑定。

### 4. 前端：一次一张、串行、混合形态

- **一次请求只传一张**，前端串行传最多 9 次。「每次最多 9 张」是业务上限，不是单请求上限。三层限制：nginx `client_max_body_size 12m` > 应用层单请求 12MiB > 单文件 10MiB。
- 上传成功后把 Markdown 语法**插到光标处**，同时在 textarea 下方显示缩略图条带；删缩略图就从正文移除对应语法。纯附件区表达不了「图放在两段话中间」，纯正文语法又看不见图。
- 单张独立状态：上传中骨架 / 失败可重试 / 可移除，不阻塞其它张。提交时若有失败中的图就拦住并提示。
- 图片加载失败（404）→ 显示占位块「图片不可用」并保留原 `alt` 文本，不交给浏览器破图图标。

### 5. 列表页不显示缩略图，只标「含图 N 张」

服务端生成缩略图要引入图片处理依赖（`golang.org/x/image` 等），与「依赖最小化」冲突；直接返原图则一次拉几十张 10MB 会拖死列表。本期列表页只统计数量，详情页才加载原图。

### 6. 上传响应 `{ id, url, content_type, size_bytes }`

`url` 即 `/api/v1/attachments/{id}`，前端直接塞进 `![]()`，零拼接逻辑。**不返宽高**：解析 webp 需要额外依赖，布局跳动先用固定比例容器兜。

### 7. 配额与清理

- 上传配额：**每人每天 50 次**，复用 `utils.Limiter.AllowWithin`。窗口沿用现有语义——**自首次上传起算的固定 24 小时窗口**，不是自然日。key 形如 `limit:upload:daily:<userID>`。
- 孤儿清理：进程内 ticker，**每小时**跑一次，单批最多 500 条，幂等条件为「三列全空且 `created_at < now() - 24h`」。范式同 `apps/api/internal/service/freeze_scheduler.go:49`。

### 8. 缓存头 `Cache-Control: private, max-age=31536000, immutable`

图片内容不可变（object_key 随机、id 不可变、软删不删对象），长期缓存能显著减少重复流量；`private` 保证不经共享代理。已知可接受风险：用户被撤权后，自己浏览器里已缓存的图仍可见——那本来就是他看过的内容。

### 9. 服务端用 `MultipartReader` 流式读，不用 `c.FormFile`

边读边写 MinIO，只把前 512 字节留在内存做 `http.DetectContentType`，全程不落磁盘、不整块进内存。

`c.FormFile` 会先 `ParseMultipartForm`：默认 `MaxMultipartMemory` 是 32MB，12MiB 请求整个进内存；调小阈值则超出部分落 `os.TempDir()` 临时文件，容器 `/tmp` 有写满风险，且超限时文件已经落盘才被拒。

### 10. 前端上传超时单独放宽

给 `requestBackend` 加可选 `timeoutMs` 参数，上传传 60000，**默认 15000 不变**。10MB 在 15s 内需要约 5.6 Mbps 上行，弱网（地铁 / 校园网）容易超；全局改 60s 则会让所有接口的「卡死」感知一起变慢。

## 拒绝的方案

| 方案 | 原因 |
| --- | --- |
| 上传端点按 scope 拆两套 | 复制 handler；草稿跨域无法互认；需给附件表加 scope 列，与 ADR 0003 冲突 |
| 上传时即带 scope | 同上；且「边写边传」时用户还没决定发到哪个域 |
| 先建空帖再传图（绑定后才可传） | 与「边写边传」冲突，会留下空帖 |
| 请求体带 `attachment_ids` 作真源 | 与正文语法形成两个真源；前端解析规则变化会悄悄改变绑定结果 |
| 请求体数组 + 正文双份校验 | 要维护两套解析，规则漂移即永远提交失败 |
| `attachment:123` 自定义 scheme | 渲染层要加自定义规则，XSS 白名单要额外放行该协议 |
| 顺序占位 `[图1]` | 图片位置由条带顺序决定，表达不了图文混排 |
| 无权访问返 403 | 确认了资源存在，可被用来枚举内部论坛规模 |
| 列表页显示原图 | 10 张 10MB 会拖死列表，移动端流量不可接受 |
| 服务端生成缩略图 | 引入图片处理依赖 + 多一套「何时生成、存哪」的机制 |
| 上传返回宽高 | webp 解码需额外依赖；布局跳动用固定比例容器兜 |
| 一次请求传 9 张 | 90MB 请求必然超时，要改全局超时，失败全丢 |
| 上传失败整体清空重来 | 已成功的 8 张白费 |
| 静默跳过失败 / 静默忽略非法 id | 用户以为图传上了，发出去才发现少了或 404 |
| 服务端静默改写正文 | 用户下次编辑发现内容被吞 |
| `Cache-Control: no-store` | 每次滚动列表都重拉原图 |
| `Cache-Control: public` | 私有内容进共享缓存等于绕过鉴权 |
| 不做上传配额 | bucket 与带宽对任何注册用户敞开 |
| 限制「未绑定附件数」 | 正常用户会被「先绑 9 张再发」卡住 |
| 上传时顺手清孤儿 | 清理与用户请求耦合，没人上传就永不清理 |
| 软删后图片仍可读 | 删帖后图片仍公开可读，等于软删没删干净 |
| `c.FormFile` + 调小 `MaxMultipartMemory` | 要么吃 32MB 内存，要么写满容器 `/tmp`，且超限时文件已落盘 |
| 全局超时改 60s | 所有接口的卡死感知从 15s 变 60s |

## 后果

**新增 2 个 HTTP 端点**：`POST /api/v1/attachments`、`GET /api/v1/attachments/:id`，都挂 `authRequired`，不新增中间件。

**新增 1 个后台任务**：孤儿附件清理 ticker（每小时、单批 500）。ADR 0003 已预告该任务，本文确定了频率与批量上限。

**新增 1 个前端基础设施改动**：`requestBackend` 加可选 `timeoutMs`（默认值不变，不影响既有接口与测试）。

**上线前必须同时改三处**（与 ADR 0002 一致，本文细化了数值）：`deploy/nginx.conf` 加 `client_max_body_size 12m`、Go 侧 `http.MaxBytesReader` + 单文件 10MiB 校验、MinIO 容器挂数据卷。

**已知可接受风险**：

- 图片缓存头 `private, immutable` 意味着撤权后用户本地已缓存的图仍可见。
- 正文里存了带 API 前缀的路径，换前缀需迁移。
- 列表页看不到图，用户要进详情页才知道图长什么样。

**可逆性边界**：「一次一张」若将来要改成批量，只需前端循环 + 后端不变；但「正文是真源」这一条一旦落地，改回请求体数组就要同时改前端解析、后端正则与所有历史数据。
